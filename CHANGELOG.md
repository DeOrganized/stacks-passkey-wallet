# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project aims to follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

**Pre-1.0 caveat:** while the library is below 1.0, breaking changes may land in
minor versions. Pin an exact version and read this file before upgrading.

## [0.4.0] — 2026-09-05

New public API — a minor bump under the pre-1.0 caveat above. Nothing in the
frozen wallet-identity definition changes; every existing address, mnemonic
and vector is byte-identical.

### Added

- **`signStacksTransaction(prfBytes, transaction, options?)`** and
  **`signStacksTransactionWithRoot(root, transaction, options?)`** — one
  generic Stacks transaction signer, designed in the open with Skullcoin
  Strike in [#12](https://github.com/DeOrganized/stacks-passkey-wallet/issues/12).
  The caller builds the transaction with `@stacks/transactions`' own builders
  (fees, nonces and post-conditions live there); the library signs exactly
  the bytes it is given, for exactly the wallet the passkey derives, and
  mutates nothing but the origin signature. Same derive → sign → discard
  discipline as `signStacksMessage`: the prfBytes entry wipes the HD root in
  `finally` on every path, including both refusals.
- **`SignStacksTransactionResult`** — a discriminated union. A standard
  transaction returns `{ kind: "complete", transaction, txid, publicKey }`; a
  sponsored transaction returns `{ kind: "origin-signed", transaction, publicKey }`
  with **no txid field of any kind** — the only txid that will ever exist is
  the one the sponsor reports after applying the fee-payer signature. There is
  no `network` or `sponsored` option: the transaction is the single source of
  truth for both.
- **`OriginAddressMismatchError`** — the origin-address fence, an initial-API
  contract rather than later hardening. Before any signature is applied, the
  account-0 address is derived for the network the transaction's own version
  byte names and compared to the transaction's origin spending-condition
  address; on mismatch the signer refuses with both addresses on the error.
  This is the "wrong passkey answered the ceremony" case caught at the last
  moment it can still be stopped. A mismatched `salt` refuses here too.
- **`UnprotectedAssetMovementError`** — post-condition mode `Allow` is refused
  by default; pass `allowUnprotectedAssetMovement: true` to sign an Allow-mode
  transaction deliberately. `Deny` mode, with or without post-conditions,
  signs normally. The library never inspects the post-conditions themselves.
- **Frozen signing vectors** at `test/vectors/signing.vectors.json` — seven
  classes (standard mainnet, standard testnet, sponsored, contract call with
  post-conditions, Allow-without-flag, foreign origin, Allow-with-flag) with
  three negative controls, every input and the exact unsigned bytes recorded.
  Generated by `npm run gen:vectors:signing`, a sibling of the derivation
  generator so that a signing regeneration can never rewrite the frozen
  wallet-identity vectors. Cross-validated at generation and at test time by
  deserializing the frozen bytes with `@stacks/transactions`, verifying the
  origin signature, recovering the public key against `@stacks/wallet-sdk`'s
  independent derivation, and recomputing the txid.

### Documentation

- README gains a **Transaction signing** section: both signatures, the result
  union, both refusal errors with the exact flag name, and what the caller
  owns — construction, fees, nonces, broadcast, and the sponsor trust boundary.
- `docs/integration.md` §3.1 documents the sponsored flow's host-side
  responsibilities — sponsor verification before paying, a server-reserved
  origin nonce inside an idempotent operation intent, persist-then-broadcast —
  as patterns pointing at the #12 checklist, not as shipped code.

### Changed

- `@stacks/encryption` is now declared as a devDependency (the test suite
  already used it via `@stacks/wallet-sdk`'s transitive install).

## [0.3.0] — 2026-08-25

### Breaking

- **`seedExportFromPrfBytes` removed from the public API.** It converts
  already-held PRF bytes to a seed phrase without a fresh passkey ceremony.
  It was never dangerous — a caller holding PRF bytes already holds the
  wallet — but its only external use is retaining key material between
  ceremonies, the pattern this library's derive-use-discard design exists
  to prevent. The function remains internal. Rationale:
  [docs/design-decisions.md](docs/design-decisions.md). With this change
  the custody claim is unconditional: **revealing a seed phrase through
  this library always requires a fresh passkey ceremony.**
  (`SeedExportOptions`, used only by the removed export, is no longer
  public either.)

### Documentation

- **Corrected to match enforcement scope.** Several claims stated
  protections more broadly than the code enforces. Each is now scoped to
  where enforcement actually lives: device-bound rejection happens in
  `createPasskey()` — the `get()`-path applies no gate today (#13, see
  docs/get-vs-create-ambiguity.md); the iOS 18.4 floor is a conservative
  user-agent check, not a capability probe; provider steering is
  host-implemented via `providerGuidance()`; memory hygiene zeroizes what
  JavaScript can zeroize (the HD root, byte buffers) while derived-key
  copies and strings are released to garbage collection. No behavior
  changed — the words now match the code.

### Fixed

- README and demo examples no longer print the recovered seed phrase to
  the console or the running page log; the demo renders it in a dedicated
  element with a dismiss that removes it from the DOM.
- The A↔B cross-device verification row now records the 2026-08-14 field
  result (Apple-ecosystem combination) instead of a placeholder.

## [0.2.1] - 2026-08-10

  or Google account can re-derive the wallet.

## [0.2.0] - 2026-07-17

Two fixes from an independent security review of the derivation and PRF core: a
testnet Bitcoin derivation-path correction and a device-bound-authenticator
gate. **Mainnet derivation is byte-for-byte unchanged** — the frozen mainnet
vectors were not touched, so existing mainnet wallets re-derive identically.

### Fixed

- **Testnet Bitcoin derivation used the mainnet coin type.** Addresses were
  derived at `m/84'/0'/0'/0/0` but encoded with the testnet HRP, producing
  `tb1…` addresses that no standard testnet wallet reproduces. BIP-84 mandates
  coin type `1'` for testnet/signet/regtest, so testnet now derives at
  `m/84'/1'/0'/0/0`. The signing path derives its key at the same
  network-correct path, so a testnet address and its signing key can no longer
  diverge (which would have made funds unspendable).

  **This changes testnet addresses.** Any testnet address produced by 0.1.0
  differs from the one 0.2.0 produces for the same passkey; testnet funds held
  at a 0.1.0-derived address are reachable only via the old
  `m/84'/0'/0'/0/0` path. Mainnet is unaffected.

### Security

- `createPasskey()` now **rejects device-bound authenticators** (Windows Hello,
  most hardware security keys) before any key derivation, by checking the Backup
  Eligibility flag in the attestation authenticator data. Previously these were
  only steered against in guidance copy, so a wallet could still be derived from
  a credential that exists on a single device and cannot be restored through
  synced-passkey behavior. Rejection raises the existing
  `PrfUnsupportedError("device-bound-authenticator")`. If the authenticator data
  cannot be read at all, the credential is rejected conservatively rather than
  assumed syncable.

### Changed

- **BREAKING:** `deriveBitcoinAccount`, `signBitcoinPsbt` and
  `signBitcoinPsbtWithRoot` take a `"mainnet" | "testnet"` network argument
  instead of a `@scure/btc-signer` network object. This makes the derivation
  path and the address encoder come from a single source so they cannot
  disagree. See [Migrating from 0.1.0](#migrating-from-010) below.
- `deriveAddresses()` is unchanged in signature and in mainnet output, but its
  **testnet** Bitcoin address changes as described under Fixed above.

### Added

- `isSyncedCredential(authData)` — a pure, unit-tested predicate for whether a
  credential is backup-eligible (synced) rather than device-bound. Exposed so
  integrators can apply the same gate at their own `create()` call site. The
  supporting `authenticatorDataFlags(authData)` and `BACKUP_ELIGIBLE_FLAG` are
  exported alongside it.
- `BitcoinNetwork` type (`"mainnet" | "testnet"`).
- Optional `network` parameter on `bitcoinNativeSegwitPath()` and
  `bitcoinTaprootPath()` (defaults to `"mainnet"`, so existing calls are
  unaffected).
- Cross-validated testnet golden vectors at `m/84'/1'/0'/0/0`, alongside the
  existing mainnet vectors.

### Migrating from 0.1.0

Callers that relied on the default (mainnet) need no change. Callers that passed
a network object explicitly should pass a string instead:

```ts
// 0.1.0
import * as btc from "@scure/btc-signer";
deriveBitcoinAccount(root, btc.TEST_NETWORK);
signBitcoinPsbtWithRoot(root, psbt, btc.TEST_NETWORK);
signBitcoinPsbt(prfBytes, psbt, { network: btc.TEST_NETWORK });

// 0.2.0
deriveBitcoinAccount(root, "testnet");
signBitcoinPsbtWithRoot(root, psbt, "testnet");
signBitcoinPsbt(prfBytes, psbt, { network: "testnet" });
```

An explicit `btc.NETWORK` becomes `"mainnet"`. The `@scure/btc-signer` import is
no longer needed for network selection.

If your integration creates passkeys, also confirm your error handling covers
`PrfUnsupportedError("device-bound-authenticator")` from `createPasskey()` — on
0.1.0 that ceremony would have succeeded on a device-bound authenticator.

## [0.1.0] - 2026-07-15

Initial release — the Milestone-1 reference library (Part A).

### Added

- Deterministic derivation pipeline: WebAuthn PRF output → HKDF-SHA256 →
  BIP-39 24-word mnemonic → BIP-32 HD root, with the Stacks account at
  `m/44'/5757'/0'/0/0` and the Bitcoin native-SegWit account at
  `m/84'/0'/0'/0/0` — byte-identical to Leather's and Xverse's account-0
  defaults.
- Frozen wallet identity (default salt `stacks-passkey-wallet/v1`, HKDF
  parameters, entropy length) with golden vectors cross-validated against
  `@stacks/wallet-sdk` and `bitcoinjs-lib`.
- Signing: Stacks message signatures and Bitcoin PSBT signing, deriving and
  discarding key material internally.
- PRF layer: passkey create/evaluate wrappers, support detection with an
  iOS 18.4 floor (user-agent check), and provider steering for Windows users
  toward Google Password Manager.
- Gated, reveal-once seed-phrase export for backup.
- Standalone browser demo and the initial documentation set (setup, integration
  guide, PRF support matrix).
